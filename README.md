# DPS Vet App

Mobile application for **Veterinaria San Roque**, built for the Universidad Don
Bosco course **Diseño y Programación de Software Multiplataforma (DPS941)**.
The app is the client-facing side of the clinic: authentication, pets,
appointments, and a personal profile.

This repository is the mobile client only. It has no backend of its own and
consumes the REST API exposed by the companion web application.

## Technology stack

- **Runtime:** Node.js 22+ and pnpm 10.16.1
- **Framework:** Expo SDK 57 with Expo Router, React Native 0.86 and React 19.2
- **Language:** strict TypeScript 6
- **Styling/UI:** NativeWind 5 (Tailwind CSS 4), Gluestack UI primitives,
  `tailwind-variants`, Lucide icons, and Reanimated
- **Authentication:** token-based sign-in against the web API; the refresh
  token is stored with `expo-secure-store`
- **Data access:** Axios REST client and TanStack React Query
- **Forms and validation:** Zod schemas shared by the form screens
- **Quality and delivery:** ESLint, Prettier, Husky, lint-staged, Commitlint,
  and Semantic Release

## Local setup

```bash
pnpm install
cp .env.example .env
pnpm start
```

The app does not run in Expo Go because it uses native modules. Create a
development build instead:

```bash
pnpm android   # expo run:android
pnpm ios       # expo run:ios
```

`ios/` and `android/` are generated by Continuous Native Generation; configure
native behavior in `app.json` and config plugins rather than editing them by
hand.

### Environment configuration

`.env.example` is the source of the local configuration contract.

| Variable              | Purpose                                              |
| --------------------- | ---------------------------------------------------- |
| `EXPO_PUBLIC_API_URL` | Base URL of the web API (its `app/api` routes)       |

The app fails at startup with an explicit error when `EXPO_PUBLIC_API_URL` is
not set. Variables prefixed with `EXPO_PUBLIC_` are inlined into the bundle, so
never place secrets in them. On a physical device or emulator, `localhost`
points at the device itself; use the host machine's LAN address (or
`10.0.2.2` on the Android emulator).

## Project structure

```text
app/
├── (auth)/                   Login, registration, and password flows
├── (client)/(tabs)/          Home, pets, appointments, and profile tabs
├── (client)/appointments/    Appointment detail and creation
├── (client)/pets/            Pet detail, creation, and editing
├── _layout.tsx               Root providers, fonts, and navigation theme
└── index.tsx                 Entry redirect based on session state
features/                     Screen logic and components per domain
components/                   Shared UI primitives (Gluestack/NativeWind)
constants/                    Permissions, roles, enums, and defaults
hooks/                        Reusable hooks (REST, notices)
lib/                          Env, token store, session engine, API errors
providers/                    TanStack Query provider
schemas/                      Zod form schemas
services/                     REST client service
types/                        Shared TypeScript contracts
utils/                        General helpers
assets/                       Images and fonts
```

Route groups in parentheses organize screens without adding those names to the
URL. Non-route code lives outside `app/`. User-facing routes include `/login`,
`/register`, `/forgot-password`, `/reset-password`, the tabs under `(client)`,
`/appointments/new`, `/appointments/[id]`, `/pets/new`, `/pets/[id]`, and
`/pets/[id]/edit`.

## How the application works

### Rendering and providers

`app/_layout.tsx` is the root layout. It loads the Geist font, global styles,
the navigation theme, and the providers: TanStack Query caching, the auth
session context, and the light/dark theme mode.

Screens are thin route files that render the matching component from
`features/<domain>/components/`. New feature UI should follow that layout and
reuse the shared primitives instead of introducing parallel conventions.

### Authentication and authorization

Authorization is permission-based, shared with the web application; there is no
role hierarchy in client code. A role is a named group of permissions stored by
the backend. The client only consumes the result and gates access to the
customer area.

The session engine in `lib/auth-session.ts` talks to these endpoints:

| Endpoint            | Use                                       |
| ------------------- | ----------------------------------------- |
| `/auth/token`       | Sign in and obtain the Firebase ID token  |
| `/auth/refresh`     | Exchange the refresh token for a new ID token |
| `/auth/logout`      | End the session                           |
| `/auth/permissions` | Load the user's flat permission list      |

Token handling:

- The ID token and its expiry live in module memory only.
- The long-lived refresh token is persisted in `expo-secure-store`
  (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`).
- All concurrent callers share a single in-flight refresh. A refresh that
  resolves after sign-out cannot resurrect the session.
- Requests carry `Authorization: Bearer <firebase-id-token>`, the same header
  the web API accepts for non-browser clients.

### Client data access

`services/rest.service.ts` owns the Axios instance: base URL from
`EXPO_PUBLIC_API_URL`, a 15 s timeout, bearer injection, a single retry after a
401 refresh, and a development logger that redacts tokens, passwords, and API
keys. Auth endpoints and `POST /users` (registration) are public and never
enter the refresh path. `hooks/use-rest.ts` exposes typed helpers on top of it,
and `features/*/use-*.ts` hooks wrap them in TanStack Query.

## Shared contract with the web application

This app and `dps-vet-web` consume the **same API**, so the following rules are
shared and must stay in sync:

- **Permissions and roles:** the catalog is seeded and owned by the web
  repository (`scripts/seed/catalog/`). `constants/permission.ts` and
  `constants/roles.ts` mirror it.
- **Domain rules enforced server-side:** clients only access their own pets,
  appointments, and medical records; appointment end times derive from the
  selected service duration; overlapping appointments are rejected; status
  changes follow a fixed state machine. The app should surface these errors
  rather than re-implement the rules.
- **Validation:** `schemas/` mirror the web Zod schemas for the same payloads.
- **Errors:** the API normalizes errors; `lib/api-error.ts` maps them for the
  UI.
- **Data and storage:** Firestore, Storage, and Firebase credentials live only
  in the web repository. This app never accesses them directly; it uses the
  REST API for all data access.

When the web API changes a request or response shape, update the matching
schemas, types, and hooks here in the same change.

## Building and delivery

Builds are produced in the cloud with EAS:

```bash
npx eas-cli@latest build --profile development --platform android
npx eas-cli@latest build --platform all
```

Application identifiers are `com.digitaldreams.dpsvetapp` (iOS bundle
identifier and Android package) and the URL scheme is `dpsvetapp`. Releases are
versioned by Semantic Release from Conventional Commits; `CHANGELOG.md` is
generated.

## Validation before delivery

```bash
pnpm check-types
pnpm lint:check
pnpm format:check
```

These checks validate static correctness only. They do not prove that the API
URL, backend credentials, or a deployed environment are configured correctly;
that requires a smoke test on a device or emulator against a running API.
